## 波形 ROM の配置（MAME `swp30` リージョン 32MB）

32bit 幅の ROM バスに 16bit ROM を 2 個並べている。MAME は `ROM_LOAD32_WORD` でインターリーブする。

| オフセット | 下位ワード | 上位ワード |
|-----------|-----------|-----------|
| 0x0000000–0x0FFFFFF | `xv364a0.ic49` | `xv365a0.ic50` |
| 0x1000000–0x1FFFFFF | `xw848a0.ic53` | `xw849a0.ic54` |

SWP30 側から見たアドレス空間: ROM 0x0000000–0x07FFFFF（32bit ワード単位, MAME 上）、
サンプリング RAM 0x1000000–0x10FFFFF。

## CPU メモリマップ（MAME より）

| アドレス | 内容 |
|---------|------|
| 0x000000–0x3FFFFF | プログラム ROM（Flash 4MB, IC24/25） |
| 0x400000–0x43FFFF | ワーク RAM 256KB（NVRAM 扱い） |
| 0x800000–0x801FFF | SWP30 マスター レジスタ |
| 0x802000–0x803FFF | SWP30 スレーブ レジスタ |
| 0xC00000 / 0xD00000 | SmartMedia（0xC00000 がデータ、0xD00000 が制御の留め金。`src/smartmedia.h`） |
| 0xC80000 | LED/スイッチ読み書き |
| 0xE00000 | LED 書き込み 2 |
| 0xF00000–0xF0003F | SIO4 (SCI4) |
| 0xF80000 | USB (M37640 経由, 未実装) |
| 0x01000000–0x0107FFFF | CPU 用 DRAM 512KB |

MIDI IN A/B は SH7043 内蔵 SCI ch0/ch1、MIDI OUT も内蔵 SCI。

## LCD（Yamaha DM113Z-5BL3、MAME では `mulcd`）

MU50/80/90/100/128/1000/2000、VL70-m、FS1R 共通のカスタム LCD モジュール。コントローラは HD44780 互換
（Yamaha 独自フォント ROM "B04" 入り）だが、**表示面はドットマトリクスの文字列ではなくカスタムセグメント**。
実機写真（2026-09-05、EX 化済み MU2000）で確認した構成:

1. 上段: 5×7 ドットの文字セル列（例 `▶000▶001 GrandPno`）
2. 中段: A1, A2, 1〜32 の 34 本のパートレベルメータ（細い縦バー）
3. 下段: 選択パート表示（例 `22B06`）、鍵盤／バンク図形、VOL・EXP のバーグラフ、PAN のダイヤル図形、
   REV・CHO・VAR の扇形、KEY の `+ 0` と ▶ マーカー。バーやダイヤルは専用セグメントで、ドット絵ではない
4. 右端: XG / TG300B / PERFORM のモード表示（レイアウト側で LED 扱い）

MAME の `mulcd` は HD44780 の DDRAM 64 セル × 5×8 ドット = 2,560 個の「画素」を出力名 `%03x.%d.%d` で外へ出し、
本物の `mulcd.svg`（525,261 byte）がそれぞれの画素をカスタムセグメントの実際の形と位置に対応付けている。
つまり **DDRAM のどのセルのどの画素が、どのセグメントか** という対応表が SVG に埋め込まれている。
本物の SVG は MAME ソースツリーに含まれず正規の入手先が無いため、`tools/dump/make_standins.py` の代替 SVG では
セル 0-23 を 1 行目、セル 40-63 を 2 行目の単純な文字列として描いている（＝実機とは配置が違う）。

対応表を自力で作る場合の方針: 実機に XG の Display Letter / Display Bitmap SysEx や MIDI を送って表示を変えつつ、
同じ操作を MAME で行い DDRAM 書き込みを記録して突き合わせる。表示の忠実度は音が出た後の課題とする。

### DDRAM の書き込み内容（MAME 上で観測）

SH7043 のポート E をビットバンギングして HD44780 を駆動（PEDR 0xFFFF83B0。bit4 = E, bit0 = R/W, bit2 = RS, 上位 8bit = データ）。
2 行モードで使用。PLAY 画面の DDRAM 内容（MAME 上で観測、2026-09-05）:

```
0x00-0x17: "         GrandP #01" C6 00 01 02 03      ← 1 行目 24 桁。末尾は CGRAM 文字 0-3（レベルメータの図形）
0x40-0x57: 89×9 11 "000" 10 "001A01" 04 05 06 07   ← 2 行目 24 桁。0x89 はパートメータ「0」の図形、0x10/0x11 は ◀▶
```

観測された ROM 図形文字コードと推定した意味（MAME 上で Edit / Util / Effect 画面を開いて確認、2026-09-05）:

| コード | 使われ方 | 推定 | 代替フォントでの描画 |
|-------|---------|------|-------------------|
| 0x10 / 0x11 | バンク・プログラム番号の両脇 | ▶ / ◀ | Adafruit フォントの三角をそのまま使用 |
| 0x14 | Edit / Util / Effect メニューの各項目の先頭。選択中の項目は空白と交互（点滅） | メニューマーカー ▪ | 小さい塗り四角 |
| 0x89 | PLAY 画面 2 行目左 9 桁 | パートレベルメータ「0」 | 下端の基線 |
| 0x87 / 0xC7 / 0xCF | 起動アニメーション（"PowerOn MU2000 EX" を囲む枠が左右から閉じる） | 枠の右 / 左 / 両側の縦線 | 2px 幅の縦線 |
| 0xC6 | PLAY 画面 1 行目 "GrandP #01" の直後 | 不明（アイコン） | 空白 |

DDRAM 0x20-0x27 に 2 行目の先頭 8 文字の写しが現れるが、これは MAME の HD44780 実装上の見え方で、表示には使われない。

メニュー画面例（Util）: 1 行目 `▪SYS  ▪DUMP ▪INIT`、2 行目 `▪MODE ▪CARD`。

## MAME での動作状況（2026-09-07 時点）

吸い出した ROM を `roms/mu2000.zip` に詰めれば MAME 0.289 で起動する。

```bash
tools
un_mame.bat                     # MIDI 入力なし
tools
un_mame.bat "loopMIDI Port"     # 仮想 MIDI ポートを MIDI IN A に繋ぐ
tools
un_mame.bat list                # MIDI ポート一覧
```

MAME 0.289 で MIDI の指定方法が変わっている。昔の `-midiin` は無い。

| 指定 | 中身 |
|---|---|
| `-midiin1` | MIDI IN A（ホストのポート名、または `.mid` / `.syx` ファイル） |
| `-midiin2` | MIDI IN B |
| `-midiout` | MIDI OUT |

PLG スロットも 3 本ある（`-plg1 plg100vl` / `plg150ap`）。

### 起動時の赤い警告は 2 つの別々の話

1. `ROMs/disk images ... are incorrect` — 代替品 3 ファイル
   （`mulcd.svg` / `hd44780u_b04.bin` / `sin-table.bin`）の件。
   **波形 ROM とプログラム ROM は MAME 登録のハッシュと完全一致していて警告は出ない**
2. `THIS SYSTEM DOESN'T WORK` — **MAME が mu2000 ドライバ自身に付けている印**。
   ROM とは無関係で、こちらから直せるものではない

実際、ロングトーンで音が暴走する現象が出るが、これは 2 のほう。
波形 ROM のハッシュが MAME 開発者の持つものと一致している以上、
データではなくエミュレーションのコード側の問題と確定できる。

### 症状の実測: 発音 150ms 後にピッチが跳ぶ

`tools/mame_audio_test.py` が、耳を使わずにこれを測る。ロングトーン 1 音だけの
MIDI を作り、`-midiin1` で流して `-wavwrite` で録音し、ピッチを時間軸で追う。

```bash
python tools/mame_audio_test.py                 # ピッチの推移を測る
python tools/mame_audio_test.py --compare-sin   # sin テーブルの影響を調べる
```

C4（261.63Hz）のストリングスで測った結果:

```
+150 ms   260.9 Hz    -5 cent   ← 正しい
+160 ms   260.9 Hz    -5 cent
+170 ms   360.9 Hz  +557 cent   ← 約 5.5 半音跳ね上がり、そのまま戻らない
```

比は 1.369 で、4/3 でも 3/2 でもない中途半端な値。**サンプルのアタック部を
鳴らし終えてループに入る瞬間**と時刻が一致するので、SWP30 のループ処理
（ループ開始位置かループ長の扱い）の問題と見られる。

49 バイトの MIDI と 20 秒のヘッドレス実行だけで再現できるので、
そのまま MAME への報告材料になる。

### sin-table.bin の代替品は音に影響していない

`-midiin1 long.mid -wavwrite out.wav -seconds_to_run 20 -video none` で
ロングトーンを録音し、`sin-table.bin` を 1/4 sin から直線に差し替えて再録音したところ、
**出力の WAV が 1 バイトも変わらなかった**。今回の音の経路では使われていない。

（2026-09-15 追記: エフェクトの無い単音での話。表は MEG の LFO が使うので、コーラス・フランジャーなどには効く。
前の代替品は形が違っていて、深いコーラスに雑音が乗っていた。doc/todo.md の `sin-table.bin` の行を参照）

この手順は MAME の音を自動で比較したいときにそのまま使える。
MU2000 は起動に約 10 秒かかるので、`.mid` の発音はそのあとから始まる。

### 音がプツプツ途切れる → -audio_latency 50

実機の出力を録音して調べたところ、**波形が 10〜30ms のあいだ直前の値で固まる**箇所が
31.5 秒に約 20 回あった（合計 410ms、全体の 1.3%）。固定値が -425 や -3169 のように
音の途中の値なので、無音ではなく**音声バッファが枯渇して直前のサンプルを保持していた**跡。

Lua でエミュ内時計と実時間を突き合わせると、30 秒に 78 回、**8〜17ms の停滞**が出る。
17ms は 60Hz の 1 フレーム。処理能力は足りている（実曲でスロットル解除時 177%）のに、
フレーム単位で落ちる瞬間があり、そこで音声が途切れていた。

```bash
mame-src\mu2000.exe mu2000 -rompath roms -bios v200 -midiin1 song.mid -audio_latency 50
```

**`-audio_latency` の既定値では 1 フレーム落ちただけで途切れる。** 50 にすると解消する
（実機で確認）。`-video none` にしてもフレームの区切りは残るので、描画を切っても直らない。
`-nosleep` `-priority 1` `-sound portaudio` `-samplerate` はいずれも効かなかった。

これは MU2000 固有の問題ではなく、MAME を Windows で動かすときの同期の話。
`tools/../run_mame_fixed.bat` には最初から入れてある。

### 残っている不完全さ

| | 状態 |
|---|---|
| 波形 ROM / プログラム ROM | 完璧（MAME のハッシュと一致） |
| `sin-table.bin` | 代替品。ただし音への影響なしを実測で確認 |
| `mulcd.svg` | 代替品。実機とセグメント配置が違う（対応表を作れば改善可能） |
| 音の正確さ | 2 箇所直した（下記）。8bit 圧縮の展開器は実機測定が必要 |

### 直したバグ

`patches/` と `mame-src/` のブランチ `swp30-pitch-bit14` に入っている。

| 症状 | 原因 | 修正 |
|---|---|---|
| ロングトーンで音色が次々変わる | `m_loop_size = m_loop & 0x3ffffff` が 26bit 取っていて、ファインチューンの下位 2bit がループ長に混入。ft>=4 の音色でループ長が 5000 万サンプルになりループしない | `& 0xffffff`（24bit） |
| 発音 150ms 後にピッチが跳ぶ | ピッチレジスタの bit14（純正が圧縮サンプルで立てる）を `if(pitch & 0x4000) pitch = 0x3fff` が誤爆し、最大ピッチに張り付く | 使用時に `m_pitch & 0x3fff` |

いずれも MAME 内部の矛盾（冒頭の仕様コメントと実装の食い違い）で、コードだけで正誤が判定できた。
実測でも確認済み: Oboe E4 は修正前 +44〜+1750 cent で暴れ、修正後は -5〜+7 cent で安定。
