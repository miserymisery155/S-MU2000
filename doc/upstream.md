
## 5. ミキサーの減衰の下 4 ビット（直した）

**症状**: パンを動かすと、音量が値によって行ったり来たりする。振り切っても鳴っている
側が大きくならない。曲のバランスが実機と違う
（[tarboh/S-MU2000#1](https://github.com/tarboh/S-MU2000/issues/1)）。

`mixer_att` の 4.4 形式の下 4 ビットは **32 分の 1 刻み**。MAME は

    (sample - ((sample * (att & 0xf)) >> 4)) >> (att >> 4)

と 16 分の 1 にしている。これだと `0x18`（0.5 × 1/2）と `0x20`（1/4）が同じ大きさに
なり、段の途中が次の段より小さくなる。`>> 5` にすると、1 から 17/32 まで下がって
次の段（1/2）へほぼ滑らかにつながる。

firmware がパンごとに書く値（左 / 右、スロットの減衰 0x18 を足す前）:
パン 1 = `00/ff`、8 = `00/39`、16 = `00/27`、24 = `01/1d`、32 = `02/17`、40 = `03/12`、
48 = `04/0e`、56 = `06/0b`、64 = `08/08`。

実機（MU2000EX、S/PDIF で録音）で 17 段のパンを測り、中央からの差を比べた
（PC80 と PC16、リバーブ・コーラスは 0）:

| パン | 実機 L / R | 直す前 | 直した後 |
|---|---|---|---|
| 8 | +3.6 / -18.5 | +0.0 / -18.7 | +3.5 / -18.4 |
| 16 | +3.6 / -11.6 | -0.0 / -30.3 | +3.5 / -11.5 |
| 32 | +2.8 / -5.5 | -2.5 / -24.2 | +2.8 / -5.5 |
| 56 | +1.0 / -0.9 | -12.1 / -1.8 | +1.0 / -0.9 |

エフェクトの送りと戻りも同じ式を通るので、曲全体のバランスも変わる。FF7 の
Still More Fighting を 1 トラックずつ鳴らすと、13 トラック中 11 が実機と ±0.6dB に入った
（直す前は -8〜+5dB）。

## 2. CMT が、割り込みを出さないときも予定を入れている

**症状**: MU 系のドライバで CPU が細切れにされ、速度が出ない。

`sh_cmt_device::internal_update()` は、コンペアマッチの時刻を必ず
「次の予定」として返す。MU2000 の firmware は CMT を **COR=1・1/8** で
走らせていて、合わせは **16 サイクルごと**に起きる。この速さで割り込みは
処理できないので、firmware は割り込みを切ってカウンタを細かい時間の
物差しとして読んでいるだけ。

それでも予定に入るので、スケジューラは 16 サイクルごとに CPU を止めて
周辺全部に予定を聞き直す。こちらで数えたら、「次の予定」を出したものの
**99.8%（2440 万回）が CMT** で、CPU は 1 サンプル（635 サイクル）のあいだに
**80 回**止められていた。

**直し方**: 割り込みを出す設定（CMCSR の CMIE）でないチャンネルは、予定に
入れない。カウンタと合わせの印は、読まれたときに計算すれば同じ値になる
（`cmcnt_r` は元から `cnt_update()` を呼んでいる。`cmcsr_r` にも同じ
追いつきを入れる）。

**効き目**: こちらでは CPU の時間が **46% 減った**（実行ループが 1 サンプル
あたり 80.5 周 → 1.5 周、実時間比 58% → 38%）。MAME でも MU 系の速度に
そのまま効くはず。

**注意**: 命令の切れ目が動くので、発音の時刻が最大 1 サンプルずれる。
こちらでは声の中身（サンプル番地・ピッチ・形式）は完全に同じままだった。

こちらのコミット: `sh_cmt.cpp` / `sh_cmt.h`

## 3. 直流が MEG から出ている（調べただけ。直していない）

**症状**: 出力に、鳴っている音の量に比例した直流が乗る。実機は乗らない。

こちらの実測では 30Hz 以下が 5.3% 残っていた（実機 0.13%）。順に潰した結果:

* ミキサの丸め（`mixer_att`）ではない。最近接・0 方向に変えても 0.3% も動かない
* 声ごとのフィルタでもない
* **声の出口は直流を持っていない**（1 声を 1 秒ぶん測って平均 −0.175、最大 1470）
* **MEG の出口が持っている**。ミキサへ入る `m_m[0x20]` / `m_m[0x21]` の平均が
  +354（最大 2667）で、出力の 13% が直流

MEG の中では `meg_pack24()` の `p >> 15`（床丸め）が軽い曲では半分を説明する
が、重い曲では動かない。残りは振幅に比例するので、掛け算側の非対称
（`m1_expand`、飽和、リバーブ RAM の詰め方）が疑わしい。

## 4. 声ごとのピッチ LFO の速さと中心（直した）

**症状**: ビブラートレートを上げると、速くなるはずのビブラートが遅くゆっくり
揺れる。伸ばした音の音程が狂って聞こえる
（[tarboh/S-MU2000#1](https://github.com/tarboh/S-MU2000/issues/1)、FF7 の Still More Fighting の矩形波リード）。

`lfo_block`（レジスタ `cccccc 001010`）に 2 つ間違いがあった。

* **step は 6 ビット**。MAME は `(data >> 8) & 0x1f` で 5 ビットしか取らない。
  firmware はビブラートレートが 72 を超えると 6 ビット目（bit 13）を立てる
  （レートを 0-127 で振って書き込みを見た: 76 で `0x6654` = step 38）。
  落とすと step 6 になり、6.4Hz のはずが 1Hz になる
* **揺れの中心は 0x800**。MAME は `(m_state - 0x400) * depth >> 11`。state は
  0-0xfff なので、これだと半分の振れ幅ぶん高い側に寄り、振れ幅も 2 倍になる。
  `(m_state - 0x800) * depth >> 12`（粗いほうは `>> 9`）で実機と合う

実機（MU2000EX、S/PDIF で録音）との比べ。PC80、2 秒の音、CC1=127:

| レート | 実機 | 直す前 | 直した後 |
|---|---|---|---|
| 64 | 5.32 Hz ±40c 中心 -7c | 5.23 Hz ±76c +39c | 5.23 Hz ±39c -9c |
| 76 | 6.43 Hz ±39c | 1.06 Hz ±93c +54c | 6.41 Hz ±38c -9c |
| 104 | 8.97 Hz ±33c | 3.55 Hz ±84c | 8.92 Hz ±33c |
| 127 | 10.62 Hz ±35c | 5.26 Hz ±79c | 10.65 Hz ±30c |

試験の MIDI は `tools` ではなく手で作った（レート 56〜127 を 2 秒ずつ）。
こちらのコミット: `swp30.cpp` の `lfo_block::type_step_pitch_w` と `get_pitch`

## 6. 声ごとのフィルタの 2 段目にも 1 段目のレゾナンスが掛かる（直した）

**症状**: オーバードライブギター（PC29）の低い音で、160Hz あたりが実機より 10dB
膨らむ。CC71（Harmonic Content）を上げると差が 20dB まで広がる
（[tarboh/S-MU2000#1](https://github.com/tarboh/S-MU2000/issues/1) の ch13）。

`filter_block` の 2 段は、レゾナンス（`filter_b` の上 5 ビット）を 1 つ共有する。
種類の bit 12 が立っている段（1, 3, 5, 7, 9, b, d, f）だけがそれを使い、
立っていない段は q=1 固定のはず（資料の「with fixed q=1」）。

MAME は `filter_b_w` の時点で **1 段目の種類だけを見て** `m_filter_p2` を決め、
2 段目にもそれを使う。PC29 は 1 段目がレゾナンス付きローパス（`16ee`、b=`8800`）、
2 段目が Q 固定のハイパス（`8280`、約 165Hz）なので、2 段目に強い山ができていた。
b を書いた後に 1 段目の種類が変わったときも、古い値のまま残る。

直し方: `m_filter_p2` には b から計算した値を常に入れ、`step()` で段ごとに
`BIT(m_filter_N_a, 12) ? m_filter_p2 : 0x80` を選ぶ（状態の形は変わらない）。

実機（MU2000EX、S/PDIF）との比べ。PC29、E2、1/3 オクターブ、全体の音量差を引いた値:

| 帯域 | 直す前 | 直した後 |
|---|---|---|
| 126Hz | +7dB | +0 |
| 160Hz | +10dB | +0 |
| 160Hz（CC71=127） | +19dB | +0 |
| 1-6kHz | ±0 | ±0 |

曲では ch13 が +2.4dB → +0.5dB になり、比べた 11 トラックが全部 ±0.5dB に入った。

こちらのコミット: `swp30.cpp` の `filter_block::step` と `filter_b_w`

## 7. 声を取り上げる途中の 1 サンプルで abort() する（直した）

**症状**: 発音数がいっぱいのまま MIDI をたくさん流すと、`streaming_block::read_8c` の
`abort()` で落ちる。MAME の MU100 でも同じように落ちる（利用者の報告）。
報告された値は `m_loop=80005302`、`m_start=40000001`。

`read_8c`（圧縮したサンプル）は、`m_loop` の bit 31（逆向きに鳴らす）が立っていると
`abort()` する。圧縮したサンプルを逆向きに鳴らす声は ROM に無いが、次の場面で一時的にそうなる:

1. 発音数がいっぱいで、firmware が鳴っている声（圧縮したサンプル、エンベロープはまだ動いている）を取り上げる
2. 次の音のレジスタを 1 つずつ書く。スタンダードキットのタム（ノート 47・48・50）は
   **逆向きの 16bit サンプル**（start `40000001`、loop `80005302`、address `00017303`）
3. start と loop を書いたあと、address を書く前に 1 サンプル進むと、前の音の圧縮の address
   （例 `ee41ae06`）と逆向きの印が混ざって `read_8c` に入る

1 回の取り上げで混ざるのは 1 サンプルだけで、次の書き込みとキーオンで正しい状態に戻る。
全パートにいろいろな音色を鳴らしながらタムを連打する MIDI（乱数で 4 通り）で、
1 曲に 0〜4 回起きた。

直し方: 逆向きのときは読まずに、直前の 4 つの値（`m_dpcm_s0`-`s3`）を返す。
実機がその 1 サンプルに何を出すかは分からないが、取り上げられる声なので聞こえる差は無い。
それまで通っていた曲の音は 1 バイトも変わらない（そこに来たら落ちていたので）。

こちらのコミット: `swp30.cpp` の `streaming_block::read_8c`

## 8. リバーブ RAM の clear を無視している（直した）

**症状**: パフォーマンスモードで、パフォーマンスを選ぶのと同時に鍵盤を弾くと、
002 Stereo Grand などが全振幅に張り付いて戻らない（issue #3）。100 のパフォーマンスのうち
002・020・033・036・043・074 で起きた。実機は普通に鳴る。

firmware はエフェクトの種類を替えるたびに、`revram_enable_w` にビットを立ててから
`revram_clear_w` に同じビットを書く（`0002`・`0004`・`0008` のように 1 ビットずつ）。
MAME の `revram_clear_w` は logerror だけで何もしない。消さないと、新しいエフェクトの
プログラムが前のエフェクトの遅延メモリの残りを読み、帰還の網が飽和したまま戻らない。

ビット i は MEG のメモリ地図 `m_map[i]` の区画（先頭 = 下 8 ビット × 1024、長さ =
2 の (10 + ビット 8-10) 乗）と読んだ。マスターとスレーブで地図が違っても、それぞれに合う。

直し方: 書いたビットの区画を、その時点の地図で 0 にする（0 は `revram_decode` で 0）。
100 のパフォーマンスを流し直して張り付きは 0。テストの曲の音は 1 バイトも変わらない。

こちらのコミット: `swp30.cpp` の `revram_clear_w`

## 9. プログラムの最後の 3 命令の書き込みがミキサに届かない（直した）

**症状**: パフォーマンス 017 FeedbackEG と 048 Warm Amp が全く鳴らない（実機は鳴る）。
XG モードでも、バリエーションを TALK MOD にしてインサーションで使うと出力が 0 になる。

m/r レジスタへの書き込みは 3 命令遅れて入る。プログラムの最後の 3 命令（`0x17d`-`0x17f`）が
書いたものは、次のサンプルの `0x000`-`0x002` で入る。ところが `sample_step` のミキサは
その前に m20-m2f の出口を読み、送りを書く。TALK MOD はインサーションの出口 m2c/m2d を
`0x17e`/`0x17f` で書くので:

1. ミキサは出口の新しい値を読めない
2. 次のサンプルの頭で、遅れた書き込みがミキサの送りを出口の古い値で潰す
3. プログラムは送りの代わりに自分の出口（0）を読むので、0 のまま抜け出せない

ヤマハのプログラムがこう書いている以上、実機はサンプルの切れ目で遅れた書き込みが済んでから
ミキサとやり取りするはず（切れ目に空きのクロックがあると見た）。

直し方: `sample_step` の頭で、遅れている m/r/index の書き込みを全部入れて空にする
（`meg_state::flush_writes`）。0x000-0x002 が 0x17d-0x17f の書いたレジスタを読むときだけ
値が 1-3 命令早く見えるが、そう読むプログラムは見ていない。

実機（MU2000EX、S/PDIF）との比べ。和音、オクターブ帯ごとの相対レベル:

| | 直す前 | 直した後 |
|---|---|---|
| 017 FeedbackEG | 無音 | 帯ごとに ±1.6dB、減衰の形も一致 |
| 048 Warm Amp | 無音 | 帯ごとに ±1dB（8kHz 以上を除く）、減衰の形も一致 |

テストの曲の音は 1 バイトも変わらない。

こちらのコミット: `swp30.cpp` の `meg_state::flush_writes` と `sample_step`

## 10. 16bit のサンプルを偶数の位置で読むと、後ろの 2 つが前の 2 つの写しになる（直した）

**症状**: 16bit のサンプルを使う音色（パフォーマンス 012 Old EP など）で、実機に無い
高い倍音と、倍音の間の雑音が乗る。低い倍音は合っている。

`streaming_block::read_16` は補間に使う 4 つの値を読む。位置が奇数のときは 3 つの dword
（`adr`・`adr+1`・`adr+2`）から取るが、偶数のときは 2 つ目の dword も `adr` から読んでいて、
`val2`/`val3` が `val0`/`val1` と同じになる。コメントの図（`bbbbaaaa ddddcccc`）では
2 つ目は次の dword。

直し方: 偶数のときの 2 つ目を `wave.read_dword(adr+1)` にする。

実機（MU2000EX、S/PDIF）との比べ。パフォーマンスモードで 1 音ずつ、全体の音量差を引いた値。
「倍音の差」は -45dB より大きい倍音の食い違いの平均、「床」は倍音の間の雑音の差:

| | 倍音の差 | 床 |
|---|---|---|
| 012 Old EP、ノート 48 | 22.2 → 2.5dB | +18.9 → +6.4dB |
| 012 Old EP、ノート 60 | 21.9 → 4.1dB | +12.4 → +5.6dB |
| 012 Old EP、ノート 72 | 8.6 → 2.4dB | +15.1 → +6.4dB |
| 062 Slap Switch（逆向きの 16bit） | 変わらず | 変わらず |

100 のパフォーマンスを C4 で比べると、012 だけが 12.8dB → 1.1dB（1/3 オクターブ帯の食い違いの
平均）になり、ほかの 99 は 1 バイトも変わらなかった。テストの曲では drums と dense が変わる。

## 11. MEG の分岐が無いことになっている（直した）

**症状**: LO-FI を使う音（パフォーマンス 007 Super Bass、097 Lo-Fi Loop）が、実機より
10dB 以上小さく、音色も違う。097 はピッチまで 49 セントずれて聞こえる。

MAME は「384 命令を毎サンプル順に回す（分岐は無い）」としていて、bit 0x3f の立った命令を
ALU の無い命令として読み流している。実際にこの命令が現れるのは、116 種類のエフェクトのうち
LO-FI（7 か所）と DYNA FLT / DYNA FLANG / DYNA PHASE（2 か所ずつ）だけ。
前後の並びから次のように読んだ:

* bit 0x20 の立った命令は、結果（p）が負か、0 かを覚える
* bit 0x3f の立った命令は、bit 0x18-0x1f の条件が合えば、bit 0x10-0x17 の番地
  （同じ 256 番地の中、必ず先）の手前まで、あいだの命令を何もしない命令にする
* 条件: bit 3 が 0 なら必ず。1 なら bit 2 が 1 で負のとき、0 で負でないとき。
  bit 1 が立っていれば 0 のときも

LO-FI では、振幅を ±m19 で止める所（`if (r01 - m19 > 0) r01 = m19; else if (r01 + m19 < 0) r01 = -m19`
の形が L と R に 1 つずつ）と、サンプリング周波数を落とすサンプル＆ホールドの間引き。
DYNA 系では `m01 = max(m01, m02)`（包絡の追従）と `m01 = max(m01, 0)`（整流）。
どれも条件の読みと辻褄が合う。分岐の命令そのものと、飛び越された命令は、レジスタも
メモリも t も触らない（書き込みの遅れの輪は普通に回る）。

直し方: `meg_state::step()` と `run_program()` に上の分岐を入れる。`tools/meg_dis.py` も
`skip to 13d if n`、`flags` のように出すようにした。

実機（MU2000EX、S/PDIF）との比べ。パフォーマンスモードで C4 を 1 音、1/3 オクターブ帯の
食い違いの平均と、音量差（ほかのパフォーマンスはおよそ +12.9dB）:

| | 帯の食い違い | 音量差 | ピッチ |
|---|---|---|---|
| 007 Super Bass（LO-FI） | 7.9 → 0.7dB | -0.6 → +14.1dB | 0 |
| 097 Lo-Fi Loop（LO-FI + 3BAND EQ + COMPRESSOR） | 5.6 → 1.1dB | +3.4 → +12.9dB | -49 → 0 セント |

ほかの 98 のパフォーマンスは食い違いが変わらない（分岐を使う種類が入っていないもの）。
DYNA 系は実機のパフォーマンスに無く、まだ実機と比べていない。テストの曲の音は変わらない。

こちらのコミット: `swp30.cpp` の `meg_cond`・`meg_state::step`・`build_ops`・`run_program`

## 12. 圧縮サンプルのループで、差分を 1 つ落とすことがある（直した）

**症状**: ループの短い圧縮サンプルを高い音で鳴らすと（パフォーマンス 041 Deep Harp の C6）、
倍音は合っているのに、倍音の間に実機に無い線が並ぶ（基音から -39dB、f0 の 1/6 おき）。
声の出力の平均値が数周期おきに段になって動く。

`read_8c` は差分を `m_pos+3` まで積算して 4 つの値を作る。ループの後ろには、先頭の 3 つの
差分の写しが置いてある（ROM で確かめた。12bit のサンプルも同じで、先頭 3 つの写しのあとは 0）。
`streaming_block::step` はループを跨ぐと `m_dpcm_pos = 3`（次に積算する位置）にしている。
1 回に 1 つ進んで跨いだならそれで合うが、ピッチが 1 より上だと時々 2 つ進む。そのときは
先頭の 1 つ目までしか積算していないのに 3 から続けるので、2 つ目の差分を落とし、
積算器がずれたまま残る。ずれは跨ぐたびに溜まる。

直し方: `m_dpcm_pos -= m_loop_size`（積算の済んだ所の続きから）。1 つ進みで跨いだときは
今までと同じ 3 になる。

実機（MU2000EX、S/PDIF）との比べ。041 Deep Harp の C6（c3 形式、ループ 44 サンプル）:

| | 直す前 | 直した後 | 実機 |
|---|---|---|---|
| 1/3 オクターブ帯の食い違いの平均 | 22.7dB | 0.3dB | — |
| 倍音 1 と 2 のあいだの床（基音比） | -57dB（-39dB の線） | -76dB | -75dB |

3 次補間そのものの誤差をこのループで計算すると -74dB で、実機の床と合う。
100 のパフォーマンスを C2・C4・C6 で比べ直し、食い違いが変わったのは 041 の C6 だけ
（ほかは 0.3dB より動かない）。テストの曲では dense が変わり、直流が 172.6 → 18.6、
30Hz 以下の割合が 17.6% → 9.6% になった（60 音を重ねて圧縮サンプルのずれが溜まっていた）。

こちらのコミット: `swp30.cpp` の `streaming_block::step`

## 13. チップの中のピッチ EG（スロット 0x0B・0x10、内部ポート 4）が無い（直した）

**症状**: 一部の XG 音色が 1〜2 オクターブ低い（DX Hard・CheezOrg が -2400 セント、SloRotar・GlaclRtr が
-1200 セント、RotaryOr が -100 セント）。ほかにも、鳴り始めに音程が動く音色（DuckLead・Bund など）が平らに鳴る。

MAME はスロット 0x0B と 0x10 を読み捨て、内部ポート 4 を 0 で返している。firmware の書き方を
時刻つきで追うと、これは声ごとのピッチ EG だった。

* スロット 0x10 は目標。下の 14bit が符号付きで、ピッチ（スロット 0x11）と同じ目盛り（1 オクターブ 1024）。
  音色の要素のノートシフト（DX Hard の -24 など）もここに入る。firmware は bit 15-14 を残して書き直す
  （`0x12E674`、`0x12E6D8`）
* スロット 0x0B の bit 14-8 は速さ。firmware は bit 15 と下の 8bit を残す
* キーオンの前に初めのレベルを書き（`0x12E004`）、キーオンの直後に最初の段の目標を書く（`0x12E710`）。
  そのあと内部ポート 4 の bit 14（着いた印）を読んで（`0x12E908`）次の段を書く（`0x12B81C`）
* 今の値は bit 14 に関係なくピッチに足す（下の追記）

直し方: 声ごとに目標・速さ・今の値・着いた印を持ち、毎サンプル今の値を目標へ近づける。刻みは音量の EG の
`level_step` を、速さから 16 引いて引く（4 分の 1 の速さ）。キーオンで今の値を目標にそろえる。

実機（MU2000EX、S/PDIF）との比べ:

| | 直す前 | 直した後 |
|---|---|---|
| 12 音色（DX Hard など）の音程の差 | -2400〜+10 セント | 全部 0 セント |
| DuckLead の鳴り始め（4ms おき、実機 -161 -117 -63 -2 +54 +86） | 平ら（+100） | -161 -117 -63 -2 +54 +86 |
| 100 のパフォーマンスの C4、1/3 オクターブ帯の食い違いの平均 | 1.37dB | 1.18dB |

速さを 16 引かずにそのまま使うと DuckLead の山が 4 倍早く、24 引くと 2 倍遅い。Bund（-75 セントから 0、60ms）
と VoxLead の揺れも同じ 16 で合う。16 より小さい速さは実機で確かめていない。

こちらのコミット: `swp30.cpp` の `peg_step`、`pitch_offset_w`、`internal_r` の 4、`streaming_block::step`

**追記（2026-09-14）**: 初めは bit 14 の立った声だけ足していた（全部足すとパフォーマンス 074・026 がずれたため）。
その後 16 の直し（遅れて鳴る層が消える）のあとで比べ直すと、bit 14 の無い値も実機では効いていた。
68/2 は 2 つの要素に 0x3E00 と 0x0200 を書き、bit 14 で分けるとエミュが実機より 600 セント低い（184.9Hz の倍音列、
実機は 261.4Hz）。全部足すと 0 セントになり、12 音色・ピッチ EG の 5 音色・Mondo（0x3C00）など 10 音色の音程は
変わらず、100 パフォーマンスの平均も 1.14dB のまま（026 は 2.4 → 1.9dB）。bit 14 が何の印かはまだ分からない。

## 14. ループ点を越えたあとのピッチの制限を、符号なしでかけている（直した）

**症状**: 元の鍵に近いピッチで鳴らす音（ピッチのレジスタが 0 付近）に強いビブラートを掛けると、揺れが片側だけになる。
Square Lead（0/81）の C5 でビブラートの深さ最大（パート 1 のビブラート深さ 0x7F、遅れ 0）にすると、実機は ±185 セントで
対称に揺れるのに、エミュは +177 セントと −20 セントの間を往復した。

ピッチ（スロット 0x11）は 14bit の符号付き（1 オクターブ 1024。0x3EEF = −0x111）。`streaming_block::step` のオクターブと
端数の計算（`((pitch >> 10) + 8) & 15` と `pitch & 0x3ff`）は、u32 のまま符号付きとして正しく働く。ところがループ点を
越えると（`m_finetune_active`）、`pitch & 0x80000000` なら 0、`pitch & 0x4000` なら 0x3FFF と、**符号なしの 0〜0x3FFF で**
範囲をかける。0x0005 に LFO の −180 を足すと 0 に張り付き、0x3F24 に +200 を足すと 0x3FFF に張り付く。

直し方: ピッチを 14bit の符号付きに広げてから LFO と微調整を足し、範囲は −0x2000〜0x1FFF でかける。ループ点の前と、
範囲に掛からないときの結果は今までと同じ。

こちらのコミット: `swp30.cpp` の `streaming_block::step`

## 15. LFO がキーオンで乱数から始まる。三角波の位相が 1/4 周期ずれている（直した）

**症状**: 同じ音を何度弾いても、ビブラートやトレモロの始まり方が毎回違う。2 層の音色で、1 回目だけ音量が大きく
落ちてから戻る（ChrchBel 96/15。issue #3 の「片方の層が早く止まる」）。

MAME はキーオンで LFO のカウンタを乱数にしている。実機（MU2000EX、S/PDIF）で同じ音を 4 回ずつ録ると、ビブラートは
4 回とも 3 セント以内で同じ形、ChrchBel のトレモロ（鋸歯状波、深さ 0x14）も 3 回とも同じだった。

* カウンタはキーオンで 0 にすると、鋸歯状波のトレモロ（ChrchBel）が実機と 3 回とも合う
* 三角波は MAME の式のままだとカウンタ 0 で一番下から始まるが、実機は中央から上がり始める。カウンタに 0x10000 を
  足して三角波を作ると、Square Lead C5 のビブラートが 900ms にわたって実機と 3 セント以内で重なる（14 と合わせて）
* 矩形波とサンプル＆ホールドは実機で確かめていない（サンプル＆ホールドは乱数のまま）

乱数は MEG のディザと同じ数列から引いているので、エミュでは引く回数を変えずに捨てている。

100 パフォーマンス（C4）の帯の食い違いの平均は 1.18dB のまま、12 音色の音程差は全部 0 セントのまま。

こちらのコミット: `swp30.cpp` の `lfo_block::keyon`、`lfo_block::tri_state`

## 16. release の速さが 0 でなければ release に入れている（直した）

**症状**: 2 層の音色で、少し遅れて鳴り始める層が立ち上がりの直後に消える（Synth Strings 0/51、Carillon 97/15、
ChrchBel 96/15 など。issue #3 の「片方の層が早く止まる」）。

firmware は層を少し遅らせて鳴らすとき、キーオンの直前に release_glo（スロット 0x09）へ 0x01xx を書く（pc 0x12E3DE）。
MAME の `release_glo_w` は上のバイトが 0 でなければ release に入れ、decay 2 の終わりでも上のバイトが 0 でなければ
release へ進む。0x01 は `^ 0x80` で 0x81 になり 1 サンプルに 0x7F ずつ落ちるので、その層は立ち上がりの直後に消える。
実機（MU2000EX、S/PDIF）では 0/51 の 2 層は同じ強さで鳴り続け、基音の山が 260.59Hz（−3dB）と 261.89Hz（0dB）に並ぶ。

鍵を離すときに firmware が書く値（pc 0x12E398）は、見た範囲で全部 0xA8〜0xF0 で bit 15 が立っている。そこで bit 15 を
「release せよ」の印とみて、release に入る条件を `& 0xff00` から `& 0x8000` にした。0/51 の 2 層がエミュでも
260.63Hz（−4dB）と 261.85Hz（0dB）に並ぶ。

100 パフォーマンス（C4）の帯の食い違いの平均が 1.18 → 1.14dB。層が欠けていた分、音量の差が普通の値（+12.9dB）に
近づいた（011 Superstrings +9.6 → +12.7、045 2 Octaves +8.7 → +11.6、090 Pad Swell +10.3 → +12.0）。

bit 15 が立っていない 0x01〜0x7F に、実機で意味があるか（遅い release など）は確かめていない。

こちらのコミット: `swp30.cpp` の `envelope_block::release_glo_w` と `envelope_block::step`

## 17. 圧縮サンプルの展開で、上限に当たると差分を 0 にしている（直した）

**症状**: XG モードの Flute（0/74）で、ノート 85〜88 にループのたびの雑音が乗る（issue #3、djtuBIG-MaliceX さんの報告）。
XG の Flute はノート 85 から圧縮サンプル 1 本（モード 0）に切り替わり、その展開で積算器が上限に当たる。
MAME の `dpcm_step` は上限に当たると差分を 0 にするので、次のサンプルから波形が崩れ、ループの繰り返しの
速さ（C#6 で約 100Hz）で基音の両側に側帯域が立つ。

報告者が実機（S/PDIF）で録った同じ試験曲と比べた（基音に対する ±40〜250Hz の側帯域）:

| | C6 | C#6 | D6 | D#6 |
|---|---|---|---|---|
| 実機 | −50.1 | −34.5 | −32.1 | −25.2 |
| 直す前 | −55.4 | −16.8 | −15.8 | −11.2 |
| 差分を 0 にしない | −55.4 | −29.2 | −25.8 | −13.5 |

4〜12kHz の量は、直す前も後も実機と 1dB 以内。上限で切り詰めるだけにする案は MUXG2K の hockinsk さん
（issue #3 のコメント）。積算器の漏れを増やしても同じくらい消えるが、モード 0 の漏れは実機で決められないので触らない。

パフォーマンスモードの 100 パフォーマンス（C4）で変わったのは 051 Deep Choir だけで、帯の食い違いが 0.70 → 0.60dB。

**追記**: 上の表の「差分を 0 にしない」の行は、エミュを MIDI どおり 1 音 0.5 秒で鳴らしていたが、実機の録音は
1 音約 1 秒で鳴っていた。側帯域に見えていたものの多くは前の音の release の尾（D#6 の −72Hz は前の D6）で、
経った時間が違っていた。テンポを合わせて 1 音 1 秒で比べ直すと、4 音とも実機と 1dB 以内で一致する:

| | C6 | C#6 | D6 | D#6 |
|---|---|---|---|---|
| 実機 | −50.1 | −34.5 | −32.1 | −25.2 |
| 直した後（1 音 1 秒） | −49.2 | −35.0 | −32.1 | −25.0 |

4〜12kHz も実機と 0.2dB 以内。

## 18. 音が止んでも 0 に戻らない。MEG の丸めが 2 か所違う（直した）

**症状**: パフォーマンスモードで 1 音鳴らして離すと、実機は約 4 秒で S/PDIF がぴったり 0（-240dB、全サンプル 0）になる。
エミュはいつまでも -66dB の雑音と直流が残る（MAME も同じ）。

原因は 2 つで、**両方直さないと 0 にならない**:

* `meg_pack24` が p（27.15）を `>> 15` で負の無限大の側へ切り捨てていた。IIR の段（マスター EQ など）が音の止んだ
  あとも 1 LSB ずつの行き来を続ける。0 の側へ切り捨てる（`p / 32768`）
* `revram_decode` が e = 0 の負の値を 0xFFFFFFE0 で反転していて、下の 5bit が反転されない。-1 を詰めて戻すと
  -32 になり、リバーブの尾に小さな負の値が膨らんで残る。`revram_encode` のちょうど逆になるよう全部反転する

同じ曲（パフォーマンス 001、C4 を 1 秒、離して 10 秒）で、鍵を離してからの 1 秒ごとの音量（エミュは実機より
約 13dB 大きいのがいつもの差）:

| | +1s | +2s | +3s | +4s | +5s | +6s 以降 |
|---|---|---|---|---|---|---|
| 実機 | -48 | -64 | -83 | -103 | **-240** | -240 |
| 直す前 | -35 | -52 | -64 | -66 | -66 | -66〜-68 |
| 切り捨てだけ | -35 | -52 | -68 | -81 | -82 | -78 |
| 反転だけ | -35 | -52 | -64 | -69 | -70 | -70 |
| 両方 | -35 | -52 | -68 | -90 | -119 | **-240** |

両方直すと、実機より 1 秒遅れてぴったり 0 になる。100 パフォーマンス（C4）の帯の食い違いの平均が 1.137 → 1.111dB
（012 Old EP 1.00 → 0.00、049 1.70 → 1.00、099 1.30 → 0.80、047 だけ 0.60 → 1.30）。
make test の曲の直流も下がった（piano +6.3 → +2.1、effects +12.0 → +6.8、bend +6.7 → +1.6）。

こちらのコミット: `swp30.cpp` の `meg_pack24` と `meg_state::revram_decode`、`swp30_jit.cpp` の同じ所
